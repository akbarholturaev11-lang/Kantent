## Automatic semantic review pipeline (enabled for clean future drafts)

Canonical feature switches are owned by `content/semantic-visual-system.json`. For newly materialized CTA-free **planned** lessons from `reviewAutoFromDate` onward, `scripts/auto-storyboard.mjs` first chooses the compatible creative treatment, then `scripts/semantic-review-integration.mjs` applies evidence-linked `semanticShot` per lesson scene to the unapproved **working review copy**. Object-only/abstract scenes have **zero automatic student characters**. A supported motion is auto-added to its uniquely authored beat only for one unnegated spoken-script cue; ambiguous, unsupported or unlinked motions stay out. The old `scene.storyboard` remains as data but `SemanticStoryScene` takes precedence when a verified timeline is present. The CTA is assembled separately from its unchanged canonical registry.

The normal Gemini TTS/transcription/import remains mandatory. Before any MP4 render, `render-episode.mjs` calls `prepareSemanticRender` to resolve the already imported **exact word timings**; a missing/ambiguous/overlapping spoken action aborts rendering, **never** silently falls back to a static building or proportional time. The compiled timeline is passed into both platform-specific Remotion props through `renderSharedPlatformVideos` and saved to `review/<id>/visual-timeline.json` with scene/cue fingerprints. The actual review MP4 uses `SemanticStoryScene`. Synthetic CI still frames do not prove real Gemini narration quality: owner must inspect the real MP4/audio. No automatic Zernio post occurs.

`productionEnabled:false` **still prohibits publishing a semantic video**, including when an owner approves its preview; publishing must be explicitly unlocked after genuine P4 visual/audio review. Previously generated, voiced, reviewed, approved and published episodes are NOT automatically rewritten or replaced. A prepared copy whose old visuals conflict with the new plan must be explicitly reworked as a separate unapproved draft, with any needed fresh registrations; never overwrite old media. The read-only `npm run content:semantic-plan -- <episode-id>` and MCP `preview_semantic_shots` remain available for inspection and do not write files.

## Published-video deduplication (verified Zernio evidence)

`content/published-posts.json` holds narrowly scoped verification records keyed by the **calendar episode ID**, platform and real Zernio post ID. Records must come from an actual connected Zernio `posts_get` readback showing `published`; a scheduled timestamp or owner-approved local package alone is never publication evidence. The schedule time does not redefine the canonical calendar date. Publication evidence **does not prove** the post was generated with the current renderer; `creativeFormatVerified:false` is intentional until an audited exported MP4 is matched.

For exactly `prepare_today_video`, resolve the calendar-local date then skip all episodes with verified published evidence. The nearest still-unpublished future `planned` entry is selected. For explicit dated production, return an already-published report rather than rerendering or overwriting the prior video. The `content:draft`, `content:make`, `content:voice` and `content:render` CLI paths also refuse duplicate generation. If a completely new cinematic edition is wanted, create a separately dated episode ID and obtain owner approval; **never change or delete published historical render/CTA/analytics versions**. The publication snapshot is not real-time and requires new Zernio verification when new posts publish.

## Automatic creative storyboard for upcoming videos

The command `prepare_today_video` resolves the calendar slot first and loads its **CTA-free** canonical lesson. The auto visual pipeline applies an evidence-grounded semantic scene plan to eligible future unapproved review copies **after** choosing the broad creative format and **before** central CTA hydration; exact voice cues are compiled only at rendering after Gemini import. See the automatic semantic review pipeline section above. `scripts/auto-storyboard.mjs` now deterministically selects the matching creative treatment from `content/creative-formats.json`, anchored at `automaticStoryboard.fromDate`, and writes the chosen `creativeFormatId` and per-scene storyboard **only into the working review copy**. The same date always gets the same compatible format, even when run another day. Already preselected compatible source formats are preserved. The CTA is then composed from the central CTA Lab. No published episode, voice profile, spoken narration, hook experiment or calendar slot is rewritten. Quiz option text must consist of genuinely authored vocabulary terms; when two suitable alternatives cannot be sourced from the lesson, the system uses compatible `problem-fix` visuals rather than inventing a question or answer. Each of the four treatments has a distinct Remotion appearance.

For existing `review/<id>/episode.json` files, an old storyboard may be migrated **only** if the saved copy exactly matches the current canonical lesson on all non-format fields, stage is `planned`/`plan-ready`, and no voice or timed captions have been produced. Modified, rendered, approved and voice-prepared copies are never silently overwritten; the command reports an actionable conflict. For eligible new work, the normal workflow generates Gemini narration and word-timed captions through the API, then renders the full review MP4 package. Profile and package approval are still required before publication.

`npm run content:viral-plan -- --json` continues to be a **read-only** reporting and experiment-planning command. It reads `content/creative-formats.json`, existing future calendar episodes and the validated Zernio feedback snapshots; it does **not** modify episodes, scripts, voice, CTA, media or publication. The hook experiment ID/format already registered on an episode remains authoritative: no automatic hook migration is authorized. The 12-post pilot is a goal, not a second calendar or an instruction to invent dates. Integrate relevant shot/beat guidance into **new or unapproved** source drafts only after genuine teaching-source verification; preserve the single learning point, current hook controls and current central platform CTA. For evidence-based decisions require same-platform/level/duration actual 7d readbacks with verified post-to-episode-to-format attribution. Never use cumulative lifetime views to claim a winning format.

This changes the earlier branch/PR requirement **for scenario-reserve source files only**. Feedback analytics and evidence reports continue using their separate process in `content/feedback/AGENT_PLAYBOOK.md`. Media generation, the voice profile, central CTA, hook/CTA history, renderer, publishing and approved/published episodes remain outside the authorization.

1. Read the current GitHub `main` commit SHA, inspect open/recent PRs and existing calendar/episode IDs to avoid duplicates, and load `AGENTS.md`, `AI_RULES.md`, `content/calendar.json`, `content/EPISODE_SCHEMA.md`, current Hook/CTA policies and this workflow. Compute the date in `Asia/Shanghai`. Count only **future**, `planned`, complete, CTA-free lesson files. Read the minimum/target and allowed weekdays only from `content/calendar.json`. Do nothing if the verified reserve reaches target.
2. Before changing a draft, open and independently verify the actual Chinese reference links, tone-marked pinyin, translations and supported grammar. Every episode needs distinct hook registration, teaching narration, Chinese cards, Russian meaning, visual beats and source receipts. Repair incomplete **unapproved future** source drafts before adding new dates; never create placeholders. New IDs/dates must not already be in `main` or a pending PR.
3. Use the **connected GitHub connector's write operations**, not a read-only GitHub fetch or an unsaved chat patch. For each existing target file, call `mcp__GitHub__fetch_file` with `ref: "main"`, keep its current blob `sha`, and call `mcp__GitHub__update_file` with `repository_full_name`, `path`, `branch: "main"`, that `sha`, a commit `message` and the **entire updated UTF-8 `content`**. For a genuinely new dated episode call `mcp__GitHub__create_file` with `branch: "main"`. Write sequentially; if a conflict occurs, re-fetch and reconcile, rather than overwriting. Update the episode JSON and canonical calendar together in the same run.
4. Re-fetch every changed file **from `main`**, re-check the actual `main` HEAD SHA, identity/calendar coherence, CTA-free status, language facts, source links, Hook registration and forbidden fields; report partial changes if one step fails. When available, run `npm run check:consistency`, `npm run content:buffer`, `npm run content:scenario-buffer` and relevant tests. Check the GitHub Actions run for the exact resulting HEAD; if CI fails, compare the failing step with the old `main` baseline, never claim CI passed, and do not knowingly leave a new regression. Explain any unresolved pre-existing failure.
5. Log actual commit SHAs, paths/dates/IDs, before/after buffer counts, `main` SHA and CI state. Do not say `main` was updated unless a fresh `fetch_file(ref: "main")` confirms it. Existing obsolete review PRs for a now-identical repair should be closed after verifying `main` contains the fix; do not duplicate their changes. Never treat committing a source draft as owner approval of a rendered video or social publication.

`npm run content:scenario-buffer -- --json` (or `--date YYYY-MM-DD` in tests) remains a **read-only** date/repair adviser; it never writes files itself. An explicit dated video request whose slot is absent is still an error: do not synthesize a new date for that production command.

## 1. Resolve the requested episode

1. Resolve relative dates in the timezone defined in `content/calendar.json`.
2. Use `list_planned_dates` and `get_production_plan`. New `content/episodes/*.json` source lessons deliberately exclude CTA. The plan/draft loader runs `composeLessonCta` against the currently approved `content/cta-lab.json` template, creating the **working** CTA snapshot. If you inspect raw lesson JSON directly, do not treat a missing CTA as a missing lesson.
3. **Owner-approved relative command:** for exactly «Бугунги видеони тайёрла» / "prepare today's video", use the calendar's timezone and the MCP `prepare_today_video` tool. If today has no entry, automatically select the **nearest future** entry with `status: planned`, disclose both dates and keep the episode's original calendar date/ID. Never rename the next episode to today, or select an older episode. If no future planned entry exists, stop and report that there is nothing to prepare.
4. **Explicit dates remain strict:** if the owner specifies a particular YYYY-MM-DD, use that exact date; if absent, report it rather than substituting another date. For requests other than the approved "today's video" command, do not silently change dates.
5. Read the current voice profile and Hook/CTA Lab active corrections before drafting.

## 2. Prepare the plan

1. Check the language examples against trustworthy references and record dated evidence. The calendar's reference facts are not independent verification.
2. Apply active Hook Lab rules. Record a dated hypothesis and one dominant opening pattern, without inventing audience-performance results.
3. Read the single `content/cta-lab.json` registry for the requested **platform**. Instagram and YouTube use `offer.canonicalRussian`; the lesson body is shared, and YouTube changes only the two supplied screenshots in the final CTA scene. Since the spoken CTA is identical, reuse the approved audio and word-level cues. A changed CTA scene needs a fresh CTA registration, final export and review; it does not need a separately written or generated lesson. The owner-approved TikTok variant uses its own manual-DM CTA and effect-led scene; TikTok publishing remains unauthorized. Call `get_platform_cta_status`; never imply automated DM delivery or invent a verified link. Normal make/render/MCP preparation automatically includes the approved YouTube ending. TikTok local review uses `content:tiktok:prepare`, `content:voice -- <id> --platform tiktok`, and `content:tiktok:render`; it writes only under `review/<id>/tiktok/` and does not update Instagram/YouTube exports. Its registration acknowledges the currently active applicable corrections. Preserve old registrations and published snapshots.
4. Finish the narration, relevant Chinese characters/pinyin/meaning, scene plan, synced visual beats, subtitles, and post text before voice generation.
5. Use the spec/schema and design token sources linked in `AGENTS.md`. An episode-level change affects its working copy; do not rewrite canonical published history.

## 3. Generate and import speech

1. Read the current provider, model, voice and approval status from `content/voice-profile.json`. While a profile is `pending-owner-approval`, generate only the sample episode named there; wait for the owner to approve that sample before using it for other episodes.
2. Run `npm run content:voice -- <episode-ID>` or the normal `content:make` workflow. It writes the exact narration and fingerprint, sends that same narration to Gemini TTS without a separate phonetic rewrite, converts the WAV response to MP3, and sends the MP3 to Gemini Transcribe for verbatim word timestamps with Russian and Simplified Chinese language hints.
3. The generator compares the normalized word sequence against the complete narration. It imports MP3 and VTT automatically only when every word matches and all timestamps are valid. After three mismatched transcription attempts, only the designated pending sample may reuse a prior sample whose exact narration, Gemini voice/model and timestamp alignment all validate; both the rejected attempt and fallback provenance are retained in metadata. For other episodes, a mismatch keeps generated files and diagnostics under `review/<episode-id>/gemini-production/<timestamp>/` and blocks rendering. Diagnose the specific mismatch before retrying; never regenerate or replace an owner-approved audio file to work around transcription.
   - For TikTok's approved manual-DM variant, pass `--platform tiktok` to voice generation so its narration, audio and word cues stay in `review/<id>/tiktok/`; do not replace the existing root review episode or its exports.
4. If a mixed Russian/Mandarin full-audio pass translates or omits spoken Mandarin syllables, recover captions from the saved audio using the same Gemini Transcribe model and provider: (a) keep the normal full-audio pass with the Russian locale from `content/voice-profile.json` and the Simplified Chinese hint; (b) isolate only the audible Mandarin spans and transcribe those clips with the Simplified Chinese hint, requesting verbatim word timestamps; (c) isolate spoken Latin acronyms such as “HSK AI” and transcribe those clips with the Russian locale from `content/voice-profile.json`; (d) save the original pass responses and each source clip's start/end offsets beside the saved generation; (e) convert each clip timestamp back to the source timeline, merge annotations in time order with the Russian pass, and map Hanzi to the episode's written phonetic token only when the character and spoken syllable are verified. Do not estimate missing timestamps or write VTT unless the existing exact normalized-token check and timestamp validation both pass. Then resume with `npm run content:voice -- <episode-ID> --resume <timestamp-folder>`. Do not change the approved voice, provider or audio.
5. The importer verifies the narration fingerprint, cue granularity, cue bounds, eligible voice profile (approved profile or its designated pending sample) and publication state. It maps timed cues to scenes, records the generated audio in `public/generated/`, and removes trailing silence only after the final timed word. There is no fixed video-duration limit.
6. Narration text and generated audio are sent to Google Gemini. Audio uploaded for transcription is deleted after the request; any deletion failure is written to the run metadata. Keep the API key only in local `.env.local`. Do not request routine file downloads or movement from the owner.

## 4. Render and validate

1. Run the existing Remotion renderer on the dated working copy after Gemini voice and captions are imported. It automatically renders the shared lesson once, each approved CTA ending, and one continuous voice/sound mix. Both final MP4s reuse identical encoded lesson frames; the join does not split the speech audio.
2. The renderer writes the Instagram package to the existing review root and the YouTube package under `review/<id>/youtube/`, each with MP4, baked-in subtitles, sidecar SRT, episode snapshot and post copy. `status.platformPackages` lists exact files, content hashes, video hashes and CTA registrations. A failed output keeps the whole job in a failed stage; do not silently omit YouTube.
3. Inspect speech/cue alignment, the last spoken phrase, tone-marked pinyin, visual relevance, shot transitions, safe areas, music/effects, on-screen readability and whether the full scenario finishes cleanly against `content/EDITING_SPEC.md` and `content/visual-system.json`. Do not impose a fixed duration limit.
4. A narration edit invalidates imported speech/timing and all downstream media; a visual or packaging edit invalidates the video, post preview and approval. Re-render and re-review before presenting as ready.

## 5. Preview, approval and publishing

1. Resolve the connected Instagram Reels or YouTube Shorts account and its platform-specific requirements through the currently authorized publishing integration specified in `AI_RULES.md`. For each exact account/platform, refresh Zernio analytics and use `analytics_get_best_time_to_post` plus `analytics_get_analytics`; consult `analytics_get_posting_frequency` when cadence affects the choice. Use the rolling lookback in `content/hook-lab.json#policy.analysisLookbackDays` and compare like-for-like platform metrics and windows. Check sync freshness and report the sample size. A slot supported by fewer than three comparable posts is provisional, not a proven optimum; show its count and supporting metric in the preview. If no fresh, usable evidence supports a candidate, ask the owner for the missing scheduling decision.
2. Use `content/calendar.json#timezone` for the proposed and scheduled local time. When deriving slots from Zernio post timestamps, convert each verified `publishedAt` from UTC into that timezone. Do not assume the timezone of `analytics_get_best_time_to_post` hour bins unless Zernio documents it; validate it against actual post timestamps first. Send an explicit IANA timezone to Zernio when scheduling and verify the returned schedule matches the approved preview.
3. Present each destination’s **actual** video from `status.platformPackages`, exact accounts, captions/hashtags, disclosures, the evidence and confidence behind the proposed time, and the immediate/scheduled posting time in the configured timezone. Instagram must use its root export; YouTube must use its YouTube export. YouTube previews include the exact title, visibility, audience selection and synthetic-media disclosure. Approval verifies the current snapshot/CTA and media hash for each selected target, and returned post records retain that binding.
4. Wait for explicit owner approval of **that specific preview**. Production authorization or voice approval is not publishing consent.
5. Only then upload/publish or schedule each platform's corresponding video through the authorized integration as a separate platform post; a single shared media file must not be sent to both accounts. Store each returned ID, status and link with its approved platform video/CTA binding. Never infer success from an ambiguous tool result or retry without checking. Immediate publication is allowed only when the owner expressly chose it in the approved preview.
6. Collect later metrics only from verifiable owner/platform readbacks; do not fabricate engagement outcomes.

## Rule changes and handoffs

Rule changes must update the canonical source and remove conflicting active copies in the same task. Follow `AGENTS.md`, run `npm run check:consistency`, and review code references that may depend on the changed setting. Historical experiment/publication snapshots are immutable evidence; do not rewrite them to appear current.

The current source of episode dates is always `content/calendar.json`. Audio settings are always `content/voice-profile.json`; current CTA wording is always `content/cta-lab.json`.
