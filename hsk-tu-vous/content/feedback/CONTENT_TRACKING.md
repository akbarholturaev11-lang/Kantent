# Content identity and feedback handoffs

This contract applies to all default production languages and all calendar content types. It does not authorize social publishing or replace the current Hook/CTA Labs.

## Stable identity

`calendar.json` owns the stable content ID and source path. Ordinary lessons use `lesson` (legacy rows may omit it); advertisements use `advertisement`; serial parts use `series-part` and their own content ID plus a common `series:{id,part,totalParts}`. Preserve existing IDs and history. A translation shares the content ID, but has its own language, source hash, voice/cues, video and approval. A platform export has its own exact video hash and publication result.

`scripts/content-attribution.mjs#contentIdentity` builds `{id,type,language,sourceHash,series?}` from the actual calendar item and exact localized CTA-free source. The SHA-256 covers `JSON.stringify(source)`; regenerate identity after any source change. Renderer output identities and hashes are candidates for review, never evidence of a publication.

## Zernio operator duties

1. Read latest `main`, typed calendar, language sources and current account connections. Use `WORKFLOW.md` for real account/platform time evidence and the exact-preview approval gate. Keep serial dates consecutive; a missing/failing part requires an explicit repair decision, never a fabricated post or an unapproved shifted date.
2. Present each final language/platform video, copy, destination, time and settings. Only after exact owner approval may the existing Zernio connection upload/create/schedule it. Check an ambiguous response before retrying.
3. After a successful Zernio GET readback, record the returned Zernio post/container ID as `zernioPostId` and the native social-network ID separately as `platformPostId`. Include platform/language, account ID/username, verified status, approved schedule/timezone or provider-returned publish time, link, exact video SHA-256, post-preview/caption hashes, content identity/hash, CTA experiment ID, approved mode/settings, approval/readback times and method, and workflow/request IDs. `publications.json`, `status.json`, `episode.json` and the per-request Codex-local receipt are the local review-package record; see `content/EPISODE_SCHEMA.md` for its field contract. `postId` is a legacy alias for `zernioPostId` only. If the native platform ID has not been returned, store `platformPostId: null` and leave the native analytics mapping pending; never infer it from the Zernio ID or a URL.
4. `scripts/codex-local-video-publish.mjs` now writes this record itself after each verified result (`scripts/publication-ledger.mjs`; `npm run content:publications -- --write` backfills from local packages, skipping receipts without recorded approval). Each record also carries `zernioPostId` (the join key for observations; `platformPostId` stays null until a provider returns it) and `creative` — experiment ID/arm, brief hash, hook ID/format/text, storytelling pattern, visual style and script hash (`content/EXPERIMENTS.md`). Preserve a durable, independently checked record in `content/feedback/publications.json#records` using the existing feedback data review/delivery process. Each mapping is `{content,platform,accountId,accountUsername,zernioPostId,platformPostId,status,videoSha256,approvedVideoSha256,approvedAt,verifiedAt,source:{provider:"Zernio",endpoint}}`. The media hashes must match the reviewed/approved package, and `content` must match that package's exact source identity. Structural validation cannot prove a provider response or owner approval; inspect the actual receipts. Update only the same verified mapping's provider-returned status, actual published time, post URL and independently verified native ID; never reassign a published native ID to different content/media. Daily Feedback may reconcile these status fields after an authenticated Zernio readback and preserve the original approved metadata; `scripts/publication-ledger.mjs#reconcileProviderReadbacks` validates the transition. A local scheduled receipt cannot downgrade a published record. Empty registry means no new verified mappings, not zero performance.

## Feedback analyst duties

Use the existing daily Feedback agent and its source verification/CI process in `AGENT_PLAYBOOK.md` (only Monday prepares a weekly experiment review). Read the durable mapping plus raw immutable observations; `loadObservations()` joins them without rewriting raw history. Unknown old mappings stay unknown. Untagged legacy language belongs only to the original series and remains separate from newly typed content. Never infer attribution from matching dates, themes, titles or similar thumbnails.

Judge each content type only by its own goal in `content/creative-formats.json#contentGoals` (`content:feedback` reports `goal` and `goalPrimaryMetric` per post); never rank an advertisement or a serial part against a lesson by one metric. Keep comparisons separate by platform, account, language, content type, serial part number, duration band, creative format, hook/storytelling treatment and actual metric window. Ads use their authored creative format without inventing an HSK level or teaching hook. Record available retention/watch, saves, shares and relevant sourced click/conversion metrics; unavailable metrics stay null. A next-part view count is not a measured part-to-part conversion without real viewer attribution. Compare part 1 against comparable part 1, and part 2 against comparable part 2; report series-level totals separately without double-counting people.

Preserve the exact provider-backed fixed-window gate: an old lifetime total is not 7d. Daily near-week 168–192h lifetime snapshots are only **directional**, never treated as exact 7d or used to justify an A/B winner. Sparse, missing or mixed-attribution evidence means **unproven/keep testing**. No automatic winner or silent Hook/CTA/voice policy replacement.

## Improvement loop

For each proposed test, save in an analytical report: test ID, owner (Calendar Reserve for source authoring), content IDs/type/language/series, baseline and candidate windows, actual sources, primary/secondary metrics, observed difference, confounders, decision (`promote`, `keep-testing`, `rollback`, `unproven`), next concrete source patch and next readback date. Missing provider windows or attribution must be named.

Feedback proposes the change; Calendar Reserve applies an owner-reviewed test to a future unapproved source under `WORKFLOW.md`, preserving the test ID in authored planning metadata. After publication the operator records exact new IDs/media; Feedback reads the next real results. Only adequate comparable primary-window evidence plus explicit owner approval can promote a policy. Keep unchanged/no-action runs quiet in external task prompts; surface a meaningful result, failure or required decision. No additional automation is created: the existing Feedback task runs daily, producing the experiment review on Mondays only. No automatic script rewriting or autonomous VIDEO publishing is added.
