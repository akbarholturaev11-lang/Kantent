# HSK AI Content — feedback agent playbook

This runbook is for ChatGPT using its already-connected **Zernio and GitHub** tools. It is not a background daemon. It requires no additional API key and collects no HSK AI application user data.

## GitHub connector writes for scheduled agents (mandatory)

Use the **connected GitHub connector's write actions** when changing repository files. A GitHub search, read-only web fetch, chat-generated patch or locally described edit is **not** a repository write. On each run, read the latest `main` and canonical project rules first; never rely on a historical feature branch or a previously cached SHA.

1. Verify repository write permission and the **current `main` commit SHA**, list open/pending feedback PRs, and inspect existing `content/feedback/observations/` and `reports/` on `main` **before creating any files**. If an earlier evidence report is still only on a review branch, reconcile it instead of silently losing it or creating duplicate dates. Read the target file with `mcp__GitHub__fetch_file` and retain its current blob `sha`. Use `mcp__GitHub__create_branch` with `base_ref: "main"` and a unique topic/date branch. Do not directly write scheduled changes to `main`.
2. For existing files, use `mcp__GitHub__update_file` with `repository_full_name`, `branch`, `path`, the **full replacement UTF-8 `content`**, `message`, and **that file's current blob `sha`**. Use `mcp__GitHub__create_file` for a new path. Write changes to the same path sequentially, not in parallel; on SHA conflicts re-fetch and reconcile rather than overwriting other work.
3. Fetch the changed files again **from the topic branch** and independently verify episode IDs/dates, Chinese facts, pronunciation, real working source URLs and the facts they support, CTA-free structure, complete scene narration/cards, hook preregistration and calendar references. URL syntax or a populated `learningFactSources` array alone is not proof that a source was checked. Preserve approved/published histories, central CTA, approved voice, render code and publishing controls.
4. Create a **review** pull request with `mcp__GitHub__create_pull_request` (`base: "main"`, `head: <topic branch>`), inspect the **exact changed-file diff**, and observe the actual PR HEAD and `mcp__GitHub__fetch_commit_workflow_runs` / `fetch_workflow_run_jobs` / job logs. **Owner instruction (2026-10-14): completed, source-verified feedback-only observations and analytical reports must ultimately be merged into `main`, not abandoned on an isolated branch**, so subsequent agents reading current `main` can find them. For such narrowly scoped data/report-only PRs, merge after validation and successful CI, then verify the new `main` SHA and fetch every changed file from `main`. If CI fails, compare the exact failing step/log with the current `main` baseline. Never merge a new regression. A *demonstrably identical, pre-existing, unrelated* CI failure may be accepted for **data/report-only changes** under this owner authorization, but explicitly report the red CI and exception; do not claim tests passed. **This feedback-only branch/merge procedure is separate from the owner's 2026-10-15 direct-to-`main` Calendar Reserve authorization in `content/WORKFLOW.md`**. That authorization permits only verified, unapproved future scenario source files and calendar entries; it does not authorize changes to central CTA, voice, renderer, published history, or social publishing. Invalidation of an old CTA registration after lesson edits is a required guardrail; never reuse stale approval.
5. Record the exact changed paths, commit SHA, PR URL, CI conclusion and merge state. **Do not report `main` delivery until independently fetching the new `main` SHA and verifying all changed files actually exist on it.** Explain clearly what was written, in which folder and why. If the write connector, source verification or workflow is unavailable, report the blocker and incomplete work, never claim it was pushed, tested, merged or published. Do not bypass a safety denial, create separate tokens or obtain HSK AI server data.

The repository's 2026-10-11 [PR #5](https://github.com/akbarholturaev11-lang/Kantent/pull/5) demonstrates branch → file SHA → sequential update → PR → checks → merge. The owner's October 14 instruction governs only feedback-data/report delivery through review PRs. A separate October 15 owner instruction permits tightly scoped, verified daily scenario-reserve source writes directly to `main`, using `content/WORKFLOW.md`; neither instruction authorizes changes to CTA, voice, renderer, publishing or approved history.

## Skill boundary for the Monday/Wednesday/Friday scheduled run

At the start of each run, read the latest `main` canonical catalog and `content/SKILLS.md`. The agent's main job remains **own-account Instagram/YouTube feedback** using the connected Zernio account and real post data; it is not a competitor scraping task or automatic content publisher.

- For analysis of existing *owned* posts, apply `content/hook-lab.json`, `content/feedback/` and the current analyzer. Do not misroute owned analytics to `ig-competitor-research`, which is explicitly for independently sourced competitor observations.
- If the agent has directly supplied/authorized external competitor Reels with independently verifiable measurements, use `.agents/skills/ig-competitor-research/SKILL.md` to write **optional read-only hypotheses** in a clearly separate research section. No observed competitor data is pasted as HSK AI results or counted in Hook Lab.
- When proposing a new Instagram publication caption to the owner (not when measuring historical post metrics), apply `.agents/skills/ig-caption-quality/SKILL.md`. Keep such proposed copy separate from canonical CTA and never silently mutate published packages or episodes.
- `ig-reel-planning` is for **new lesson editorial drafts** during Calendar Reserve, not the analytics run; do not author new scripts as a side effect of this job. If the evidence suggests a test, report a proposed hypothesis for a future separately authorized lesson.

## Analysis run (external ChatGPT schedule: Monday / Wednesday / Friday, Asia/Shanghai)

1. Fetch the latest GitHub `main` SHA and read the **current** `hsk-tu-vous/AGENTS.md`, `AI_RULES.md`, `content/calendar.json`, `content/hook-lab.json`, `content/cta-lab.json` and this playbook. Check all pending feedback PRs plus current `main` observation/report files first. Avoid repeated or missing historical report snapshots.
2. **First call connected Zernio `accounts_list` and verify current account IDs/platforms; never assume an account is connected because old Zernio posts mention it.** Historical checked examples (2026-10-14 and 2026-10-28): Instagram `hskai.app` and YouTube `hskai_app` were connected; TikTok was not. **These are not current-account guarantees**. Re-check this every run: collect real observations separately from currently connected Instagram and YouTube, not TikTok historical publication metadata. Never present legacy `posts_list` TikTok IDs or `published` statuses as independently verified active TikTok media or analytics. Only consider another platform after verifying its actual current connection and platform-specific post evidence. Read horizon and windows ONLY from `content/hook-lab.json#policy` (rolling 30 days by actual `publishedAt`; `24h` early signal; `7d` primary). Preserve actual platform post ID, URL, timestamps, metric units, source/provider refresh times and account ID. If platform/provider history coverage is less than 30 days, report the coverage gap. Missing/unavailable or unsupported provider metrics are unknown/null, never assumed zero.
3. Add append-only, provenance-stamped **separate per-platform** snapshots in `content/feedback/observations/` following the README and schema; never overwrite old measurements or silently replace them with fresh cumulative values. Create a dated Instagram + YouTube report in `content/feedback/reports/` and link the actual evidence files. For cumulative Zernio totals use `window: "lifetime"`, not fabricated exact 24h/7d windows; a provider daily cumulative timeline does not automatically certify exact elapsed-post-age windows.
4. Match source `episodeId` / hook format / HSK level / effect style only if the published media and existing episode source prove the mapping. Unverified fields remain `null`.
5. Inspect the read-only `content:feedback`, `content:viral-plan` and `content:buffer` reports. For a new cycle create a dated feedback report containing OBSERVATION, HYPOTHESIS, EXPERIMENT and DECISION sections, plus source links and uncertainty. Only source-verified `24h` may provide an early signal; only source-verified `7d` within the rolling 30-day publication cohort may support a primary recommendation. Require verified episode-to-post mapping, matched platform, same window, level, duration band, minimum comparable post sample and views. No lifetime/72h substitution. Never infer a 24h or 7d result simply by waiting 24h or 7d before fetching cumulative lifetime.
6. If calendar/read-only diagnostics show a missing or incomplete future scenario reserve, record the concrete dates/IDs, per-language gaps, and whether the reported count is Russian-only. **Do not write or repair any episode, translated lesson, motion graphic or calendar row in a Feedback run.** Hand the factual shortfall to the separately scheduled Calendar Reserve agent under `content/WORKFLOW.md`; no automatic cross-agent run is implied. This analytic task's GitHub PR must contain only feedback observations and reports.
7. **Do not modify scripts, future plans or creative policy as a feedback side effect.** For an eligible primary fixed-age `7d` cohort with verified post-to-episode/hook/HSK/format provenance, calculate descriptive matched comparisons and document the Hook Lab sample/lift/secondary-metric criteria; these are still not proof of causality. Record a proposed future experiment and seek separate owner approval/authoring authority before any production rule change. If data are lifetime-only or unlinked, mark `insufficient-evidence`. Never modify CTA wording, voice, approved/published snapshots, render code, calendar or social publication.
8. Commit through a branch/PR, run or inspect repository tests/CI (always disclose test gaps and existing baseline failures), and for validated feedback-only data/reports complete the controlled `main` integration described above. Finally fetch all reported file paths from `main` and verify its commit SHA, and summarize Instagram/YouTube metrics, provenance gaps, exact changed files, PR, merge commit, CI conclusion and whether main contains every file. Never claim unattended execution unless the scheduled task actually confirmed it.

## Production handoff only (not a Feedback-agent action)

When a separately owner-invoked **video production agent** prepares media, that agent re-reads the current `main`, matching episode, language-specific Hook/CTA Lab and voice/visual rules and captures the source SHA. Changed sources invalidate stale previews and require fresh review under `content/WORKFLOW.md`. **The Feedback agent must not start production, generate voice, alter reviews or invalidate media during an analytics run.**

## Storytelling pattern evidence

For adaptive script comparisons, an optional observation `storytellingPattern` can be `direct`, `single-rehook` or `layered` only **after** proving the published media corresponds to the exact episode/narration story version and verified Hook, HSK level and creative format. Save that provenance with source records, not guesses based on thumbnail or lesson topic. Missing mappings remain `null`, not defaulted to direct. `feedback-analyzer.mjs` groups eligible fixed-age 7d observations by verified pattern, platform, level, duration band and Hook format, but does **not** by itself prove comparable creative format assignment, lift/guardrails or a winner; it never treats provider lifetime metrics as fixed post-age observations. Owner sign-off remains necessary before any learned policy is promoted.

## Non-goals

No customer-install attribution, no separate social API token, no user data extraction, no causal claim from views alone, no automatic winner declaration, no autonomous publishing. Existing owner approval of the exact final preview remains mandatory.
