# HSK AI Content — feedback agent playbook

This runbook is for ChatGPT using its already-connected **Zernio and GitHub** tools. It is not a background daemon. It requires no additional API key and collects no HSK AI application user data.

## GitHub connector writes for scheduled Feedback (owner migration 2026-11-09)

**Owner instruction 2026-11-09 supersedes the 2026-10-14 feedback branch/PR requirement.** This scheduled Feedback agent writes verified, append-only analytics **directly to current `main`**, without a topic branch, PR or PR-CI wait. This permits **new files under `content/feedback/observations/` and `content/feedback/reports/`**. A second narrowly scoped owner authorization dated 2026-11-17 permits verified *publication readback status reconciliation* in `content/feedback/publications.json`; see the section below. No script, locale, calendar, Hook/CTA policy, voice, renderer, publishing, DM or other repository file may be modified by Feedback, **except the narrow, verified existing publication-ledger status readback** defined below. Calendar Reserve's distinct direct-main source-drafting authority remains governed by `content/WORKFLOW.md`.

1. Before writing: confirm actual Zernio connections and fresh provider evidence; read current `main` SHA, canonical rules, existing observations/reports and pending feedback PRs. Reconcile earlier PR-only reports without duplicating their snapshots. A repeated provider snapshot is a **no-op**.
2. Validate provenance, exact window evidence, IDs, schema, units, unknown/null semantics, and the proposed report. Run available read-only consistency checks if executable. If validation or source access is insufficient, **skip the write** and report the blocker.
3. Use the connected GitHub connector `create_file` on **`main`** for each new append-only observation/report. If a same-date file already exists, never overwrite it: compare evidence and either skip the duplicate or create a distinct dated+collection-timestamp path for genuinely new measurements. `update_file` is permitted for a necessary, explicitly reconciled correction to an existing feedback report **or the strictly limited provider-confirmed status readback in `feedback/publications.json` below**, using the latest fetched blob SHA; never rewrite prior raw observations. Fetch the fresh `main` HEAD immediately before writes; if another agent moves it, re-read affected paths and reconcile before continuing. Never force push.
4. After each write, fetch the file back from `main` and verify its bytes, source IDs and metadata. Fetch final `main` HEAD and all new files again. Check the actual GitHub Actions runs associated with the resulting `main` commit, including failures or pending checks; direct writes cannot wait for PR CI, so **never claim CI passed before it actually completes**. Report any regression explicitly and do not perform unrelated repairs under this agent.
5. Report exact paths, final `main` SHA, provenance/window/confidence, duplicate/skipped counts, CI status and remaining gaps. If GitHub denies writes, stop and report the failure; do not fall back to a branch/PR unless the owner changes this policy. This authorization does not imply approval for video or social publishing.

The agent's main job is **owned video-account feedback** using current Zernio connections and real post data from the language-matched Instagram, YouTube, TikTok and Facebook destinations; Telegram is a **separate factual Tajik product-news text + original 4:3 image** channel (owner-authorized automatic publication via `content/telegram-agent.json`) and remains outside VIDEO analytics. The Feedback agent does not publish anything.

- For analysis of existing *owned* posts, apply `content/hook-lab.json`, `content/feedback/` and the current analyzer. Do not misroute owned analytics to `ig-competitor-research`, which is explicitly for independently sourced competitor observations.
- If the agent has directly supplied/authorized external competitor Reels with independently verifiable measurements, use `.agents/skills/ig-competitor-research/SKILL.md` to write **optional read-only hypotheses** in a clearly separate research section. No observed competitor data is pasted as HSK AI results or counted in Hook Lab.
- When proposing a new Instagram publication caption to the owner (not when measuring historical post metrics), apply `.agents/skills/ig-caption-quality/SKILL.md`. Keep such proposed copy separate from canonical CTA and never silently mutate published packages or episodes.
- `ig-reel-planning` is for **new lesson editorial drafts** during Calendar Reserve, not the analytics run; do not author new scripts as a side effect of this job. If the evidence suggests a test, report a proposed hypothesis for a future separately authorized lesson.

Check all pending feedback PRs plus current `main` observation/report files first. Avoid repeated or missing historical report snapshots.
### Publication readback — owner authorization 2026-11-17

On each daily run, check every relevant tracked approved Zernio publication record whose status is not fully reconciled, via the authenticated language/account-matched Zernio connector. Compare **Zernio post ID, exact platform and account ID** to the existing approved ledger record. A provider-confirmed `published` result supplies actual `publishedAt`, native `platformPostUrl`, and `platformPostId` ONLY when the provider explicitly returns that ID. Scheduled readbacks are no-ops and cannot downgrade published posts. Before writing validate the source and account, inspect the current content and abort on conflict. ### Native identity fallback from an authenticated published URL (owner override 2026-11-18)

The owner explicitly authorized a **narrow alternative** to the earlier provider-native-ID-only rule where a connected Zernio response confirms publication but does not expose a numeric or platform-specific native ID. This supersedes **only** the blanket "never derive from URLs" phrase above, subject to ALL conditions:

1. Use the **exact** existing approved `zernioPostId`, accountId, platform and `published` readback from the matching connected account. The provider itself must return the canonical native `platformPostUrl`. Unpublished, URL-only search hits, account mismatches and guessed associations are prohibited.
2. For YouTube `https://www.youtube.com/watch?v=<11-character-id>`, the URL's `v` value **is the video ID**. Cross-check its extraction against a matched RU published video for which a provider native ID already exists. Then write `platformPostId` to that `v` ID **only if currently null**, with `source.urlIdentity` declaring `kind: "youtube-video-id"`, value, canonical URL, extraction method, and **`provenance: "url-derived-not-provider-field"`**. This is never described as a provider-returned ID.
3. For Instagram `/reel/<shortcode>/`, the shortcode is a valid **public URL identifier**, **not** the provider's numeric `platformPostId`. Observed RU verified examples show that converting an Instagram shortcode into a large media number does **not** reproduce the provider's Graph API-style platformPostId. Save the shortcode separately at `source.urlIdentity` with `kind: "instagram-reel-shortcode"`; leave `platformPostId: null` until a provider or separately verified supported endpoint returns the correct numeric identifier. Never put the shortcode or decoded media number into the numeric-ID field.
4. Do not change approved video/source hashes, platform/account, CTA or experiment assignment. Never overwrite a conflicting existing ID; stop for reconciliation. Never extend this fallback to TikTok/Facebook or infer identity from title/date. `scripts/content-attribution.mjs` can already join the approved Zernio post ID when native ID is missing; native numeric ID is not a prerequisite for such a verified join.
5. Validate the complete ledger, re-fetch current blob SHA, update only existing approved published rows and provenance; verify changed fields and CI. Zernio native-ID absence remains a known connector limitation, not "provider confirmed". Scheduled Feedback may perform only this scoped correction; no media publication, scripts, policy promotion or general URL guessing.

This is a **status-only exception** to Feedback's normal append-only reporting authority. It is not permission to create publication records, scripts, voice, video, calendar, experiment arms or social media posts. A scheduled Feedback run never re-publishes video.

## Experiments readout (owner 2026-11-17, `content/EXPERIMENTS.md`)

On each daily run, seek a provider-backed snapshot for each active-test post aged 168–192 hours, keeping its exact `publishedAt`/`observedAt`; this is a **directional near-week cumulative** readback, never provider-exact `7d`, and cannot justify promotion. On the Monday run, run `npm run content:experiments -- --review --write` and add the dated `content/feedback/reports/<date>-experiment-review.md` with the other append-only files (skip if it exists). Report each test's goal, styles, per-arm results, recommendation and reason, and propose the next test with evidence. Never fill in missing data, force a weekly winner, change `experiments.json`, scripts or policy; a promotion is proposed to the owner only.

## Production handoff only (not a Feedback-agent action)

When a separately owner-invoked **video production agent** prepares media, that agent re-reads the current `main`, matching episode, language-specific Hook/CTA Lab and voice/visual rules and captures the source SHA. Changed sources invalidate stale previews and require fresh review under `content/WORKFLOW.md`. **The Feedback agent must not start production, generate voice, alter reviews or invalidate media during an analytics run.**

## Storytelling pattern evidence

For adaptive script comparisons, an optional observation `storytellingPattern` can be `direct`, `single-rehook` or `layered` only **after** proving the published media corresponds to the exact episode/narration story version and verified Hook, HSK level and creative format. Save that provenance with source records, not guesses based on thumbnail or lesson topic. Missing mappings remain `null`, not defaulted to direct. `feedback-analyzer.mjs` separates eligible fixed-age 7d observations by verified pattern, platform, level, duration band, Hook **and** `creativeFormatId` (with an explicit unverified bucket), but does **not** by itself prove a causal lift, secondary guardrails or a winner; it never treats provider lifetime metrics as fixed post-age observations. Owner sign-off remains necessary before any learned policy is promoted.
